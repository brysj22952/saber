## 2. 走哪条路？——「重新提交现有版本」，不是「新建版本」

### 2.1 结论

**在 AGC 里对一个「待修改」的版本重新提审，不需要新建版本**：
就在这个 1.0.2 版本页上改表单，然后点「提交审核」。

**证据（本项目自己的操作史）**：上面 §1.2 的版本历史 —— 同一个版本条目
（versionId `2079739086494559168`）已经三次被打回、三次在**原条目上**重新提交，
每次都是「准备提交 → 预审中 → 正在审核 → 待修改」循环，没有另建版本。
另外当前版本表单上「提交审核」按钮就是可点的，文件框也都是可编辑的 ——
平台明确允许就地修改后重新提交。

### 2.3 最终推荐：**上传 1.0.3 再提交**（2026-11-20 复核后）

「重新提交现有 1.0.2」这条路径**技术上确实存在**（实测：1.0.2 处于「待修改」时表单可编辑，
点「提交审核」会弹出「发布信息确认」，里面写的是 **软件版本号：1.0.2(1000002)**）——
所以「不传新包直接重提」不是死路。

但**仍然推荐先传 1.0.3**，理由都是实测出来的：

1. **1.0.2 的包内中文界面还自称「Saber」**。中文 locale 的 19 处改名是 11-18 才做的
   （第 4/6 轮），而 1.0.2 的包是 **11-17 20:36** 构建的 —— 也就是说 1.0.2 里
   「使用 Saber 登录」「Saber 的 Nextcloud 服务器」「关于页版权声明」等中文文案**全是旧名**。
   第 2 轮被判「名称/图标与已有 Saber 应用相似」是**阻塞项**；审核员只要切到中文看一眼，
   1.0.2 就有再撞一次知识产权问题的风险。1.0.3 里 24 个语言包全部改成了「赛博手写笔记」。
2. **1.0.3 去掉了 Sentry**（第 7 轮）。商店「权限说明」白纸黑字写着「不采集崩溃日志」，
   而 1.0.2 的包里**还带着**上游作者的 Sentry DSN —— 审核员点「同意」就会把崩溃数据发给第三方。
3. **1.0.3 启动不再联网查更新**（构建时 `UPDATE_CHECK=false`）。1.0.2 每次启动都会向 GitHub 发请求，
   与商店「完全离线可用」「未开启同步前不发出任何网络请求」的承诺对不上。
4. 审核报告里那两条「可提升项」——「切换语言后部分中文没有变化」「导入 PDF 无响应」——
   在 1.0.3 上至少名字相关的那一半不会再出现（导入 PDF 无响应是鸿蒙版**没有 PDFium** 的能力缺失，
   报告已明说不阻塞）。

**代价**：多花 20 分钟上传一个 16.51 MB 的包（首尔机本地已有，本机也有同 md5 副本：
`D:\saber-oh\release-staging\ohos-default-signed-1.0.3.app`，md5 `0094975E96179B44F0CFF396702CE025`
与首尔机 `build/ohos/app/ohos-default-signed.app` 一致 ✓）。

**若时间紧**：先按 §3 原地重提 1.0.2（步骤完全一样，只是第 4 步不换包），
被再打回再上 1.0.3。

### 2.4 「重新提交现有版本」这条路到底怎么走（实测确认）

1.0.2 处于「待修改」时：表单**可编辑**（所有文件框 `disabled=false`）、
「保存草稿」**disabled**、「提交审核」**可点**、左导航节点文字是「1.0.2 待修改」。
点「提交审核」后弹「发布信息确认」弹窗（见 §1.5），
里面写「软件版本号：1.0.2(1000002)」——说明表单里的包**确实已经选好了**，
「发布版本」那一栏显示的「去选择」按钮是**占位假象**（历史已知，不是没选包）。
所以原地重提的最小动作 = 填备注 +（可选）传附件 + 点提交审核 + 确认提交。

| | **方案 A（推荐）：原地重新提交 1.0.2** | 方案 B：上传 1.0.3 再提交 |
|---|---|---|
| 动作 | 不动包，只传资质材料 + 写备注 + 提交 | 先上传 1.0.3 的 .app → 版本页「去选择」换包 → 传两个附件 → 写备注 → 提交 |
| 与客服口径 | ✔ 完全一致（"保持当前名称及图标重新提审"） | ✔ 也一致（1.0.3 的名称/图标与 1.0.2 相同） |
| 成本 | 10 分钟，不用构建、不用传包 | 需要把包传到 AGC（16.51 MB）+ 重新选包 |
| 能修掉报告里那 2 条「可提升项」吗 | ✗ 不能（报告说不阻塞） | 能顺带修掉：Sentry 已移除、启动不再联网查更新、24 个语言包旧名已改 |
| 风险 | 「导入 PDF 无响应」在鸿蒙版是**已知能力缺失**（无 PDFium），审核员再测一次仍会写进报告，但**不阻塞上架** | 换包后「发布版本」可能被重置（历史上踩过），且要重新选包 |
| 什么时候用 | 想最快过审、先把上架拿下 | 愿意多花 30 分钟，把审核员爱测的那两处一并修掉 |

> **建议**：先用方案 A 过审上架；1.0.3 的改进（Sentry 移除、启动不联网、24 语言包改名）
> 上架后作为常规更新发 1.0.4。
> 如果方案 A 提交时被平台以「版本无变更 / 版本号重复」拒绝，再改走方案 B。

## 3. 逐步手工 checklist（方案 A：原地重提 1.0.2 —— 备用路径）

> 全程在**华为应用市场 · AppGallery Connect 控制台**里操作：

> 左侧要能看到「APP与元服务 → 应用上架」，账号是 `130******20`（胡中强）。

### 步骤 1 · 进入 1.0.2 的版本表单

1. 打开 AGC 控制台 → 顶部「应用上架」（或左导航「APP与元服务 → 应用上架」）。
2. 进入应用「**赛博手写笔记**」。
3. 左侧导航（新版 UI 是**两级**）：
   **应用上架 → 版本信息 →「1.0.2 待修改」**
   （「版本信息」下面挂着各个版本节点，节点文字自带状态；本次就是「1.0.2 待修改」）
4. 页面顶部会出现 `1.0.2 新版本 - 待修改` 与 `状态：待修改`，右上/页内有
   「保存草稿」「**提交审核**」两个按钮。

> 也可以走左导航「版本信息 → **版本历史记录**」看每轮审核意见与「审核报告」链接。

### 步骤 2 · 填「备注：」（**客服要求的字段，必做**）

* 位置：版本表单往下滚到 **「应用审核信息」** 区域 →
  「如果您的App部分功能需要用户进行身份验证…」说明文字下方 →
  「需要登录进行审核」勾选框 → 再下一行就是 **「备注：」**
  → 再下一行是「自测文件：」。
* 形态：一个多行文本框（textarea，5 行），右下角有字数计数 `0 / 300`。
* **上限 300 字；选填，不是必填**（无红星、无校验报错）。
* **原文粘贴这一句，不要改写、不要加标点、别用英文引号**：

```
已通过互动中心工单号：461323199043685201反馈，当前名称及图标与Saber不一致，已沟通。
```

  （共 53 字，远小于 300 上限；工单号 18 位数字一个都不能错）

* 贴完确认计数变成 `53 / 300`，且文本框里没有换行、没有多余空格。

### 步骤 3 · 传「授权书及其他材料」（消除唯一阻塞项）

* 位置：版本表单 → **版权信息** 区块 → 最后一项「**授权书及其他材料：**」→ 点「上传」。
* 传这个文件（首尔机本地路径，仓库里也有）：
  `/root/hzq/saber-ohos/saber/harmony/docs/store-materials/授权材料.zip`
  （624,909 字节，内含两份 PDF：`GPL-3.0-LICENSE.pdf`、`开源说明与授权依据.pdf`）
* 控制台原文限制：「请上传 zip 格式文件，不能超过 200M。压缩包内支持包含 JPG、JPEG、BMP 格式图片和 PDF 格式的文件，文件夹层级最多三层，累计不超过 200 个文件。」
  → 我们的 zip 里就是两份 PDF，**合规**。
* 顺带：同区块的「审核附件」当前是旧的 `审核附件.zip`（只含 .txt 文本）。
  如果能替换，建议一并换成 `harmony/docs/store-materials/saber-open-source-audit.zip`

  一节，正是回应审核员「与 Saber 名称/图标相似」那条的依据。
  能否直接替换：**需用户确认**（点开该槽看是否给出替换入口）。

### 步骤 7 · 提交后跟踪

* 页面位置：左导航「版本信息 → 版本历史记录」看状态时间线；
  版本页顶部看 `1.0.2 新版本 - 预审中 / 正在审核`。
* 脚本轮询（首尔机，**只能有一个实例**）：

```bash
pkill -f "agc_poll_review[.]sh"          # 先清掉旧实例
cd /root/hzq/saber-ohos/saber
nohup env AGC_POLL_INTERVAL=300 bash harmony/toolchain/agc/agc_poll_review.sh >/dev/null 2>&1 &
```

## 6. 已知的坑（照着做时避开）

1. **「保存草稿」会清掉已选的包** —— 提交前最后一步才点「提交审核」。
2. **离开版本页会重置「发布版本」** —— 顺序：选包 → 传附件 → 改文案 → 提交。
3. **「去选择」按钮看着像没选包** —— 多半是占位假象，但要按步骤 4 复核一次。
4. **上传文件后 DOM 会重建** —— 脚本化上传时每传一个都要重新取 nodeId。
5. **`el-cascader`（应用分类）不吃 JS 合成事件** —— 必须真实鼠标事件。
6. **控制台会话久了会被重定向到「华为 APIs 使用协议」页** —— 重载一次即可（SPA 按 hash 回到原路由）。
7. **别点「撤销审核」** —— 那会把已提交的版本退回可编辑并要重走预审；现在这个状态本来就是可编辑的。
8. **提交后 36 小时内别点「催审」**。
9. **离线/编码坑（脚本相关）**：PowerShell 读文件写脚本要用
   `[IO.File]::ReadAllText($p, [Text.Encoding]::UTF8)`，
   否则中文被按 ANSI 读成乱码且会吞掉换行；脚本要写文件再传，不要在一条 ssh 里嵌套多层引号。

## 8. 2026-11-20 实测补遗（本轮新增,优先看这一节）

### 8.1 1.0.2 的包是**发布签名**,不是调试签名（实测,已排除「签名被拒」的猜测）

### 8.3 标签页坑（写脚本的人注意）

AGC 控制台是 Vue SPA，**不同模块可能渲染在不同的浏览器标签页里**：
本轮实测浏览器里同时存在两个 page target ——

* `…/agc/index.html#/auditReportView`（审核报告页，由版本历史里的「审核报告」链接新开）
* `…/agc/index.html#/myApp/6917621319756237551/…`（应用详情/版本表单页）

`agc_console.py` 的 `CDP` 类连的是 `/json/list` 里的**第一个 page**，
标签页顺序一变就会读到另一个页面 —— 本轮因此把审核报告页误当成应用页。
**查状态、抓报告、读表单都要先确认连的是哪个 target**，不要假设都在主标签页。

上传 1.0.3 → 选包 → 传两个附件槽 → 补截图/文案 → **填备注** → 提交审核 → 确认提交。
