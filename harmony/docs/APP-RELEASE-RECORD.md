### 第 3 轮真正卡住的地方(不是审核,是控制台自己拦着)

控制台一直挂着一条横幅:**「您的 应用信息 页面还有必填信息未填写,请前往修改。」**
可应用信息页的必填项(名称 / 三个设备页签的图标 / 分类 / 标签 / 语言 / 支持设备)**全都填好了**,
点「提交审核」也**没反应**(不弹框、不报错)。

真凶是**勾选了「平板」这个设备类型**:一旦勾上,应用信息页多出一个「平板」页签,
控制台就一直认为有必填项没填,提交被拦在前面。
把「支持设备」改回 **手机 + PC/2in1**(和上一版一样)后,横幅立刻消失,提交一次就过了 ✓。

> 结论:鸿蒙版目前只在 **手机 / PC(2in1)** 上验证过平板形态,
> 平板的支持暂时先关掉 —— 等真机上把平板形态跑顺了再打开 ✓。

### 第 3 轮踩到的另外两个坑

1. **版本页离开时「发布版本」会被重置**:改完介绍/截图再选包,顺序不能乱 ——
   要**先选包、后改文案与截图**,否则一离开页面,选中的包又变回「去选择」。
2. **提交是两步**:点「提交审核」后会弹「发布信息确认」
   (软件版本号 / 默认语言 / 发布国家或地区),要再点一次「**确认提交**」才真正进预审 ✓。

## 审核期间的操作约定

- **别点「撤销审核」**,除非确定要撤回;那会把已提交的版本退回到可编辑状态,
  而再次提交又要重新走一遍预审 ✓。
- **「催审」** 只在排队明显超时(例如提交满 24 小时仍无动静)时点一次 ✓,
  提交 20 分钟内点它没有意义,反而可能被当作骚扰 ✗。
- **审核期间别再点「保存草稿」**,它会清掉「发布版本」里已选的包 ✓。
- **期间可以改的**:应用图标、应用分类/标签、协议服务里的协议 —— 这些不影响已提交的版本快照;
  **不能改的**:版本表单里的包、截图、介绍等,要在改完后重新提交版本才生效 ✓。

## 若被打回(预审不通过 / 审核驳回)的处理流程

1. 打开 AGC → 应用管理 → Saber → 版本/升级 → 点「检测报告」或「审核意见」,**先把报告原文贴进本表**。
2. 按报告逐条修,常见对应关系:

   | 报告里常见的说法 | 怎么处理 |
   |---|---|
   | 「隐私政策 URL 无法访问 / 与应用功能不符」 | 改 `harmony/docs/privacy-policy.html`,推 gh-pages 后重填隐私政策网址 |
   | 「权限说明与实际申请不符」 | 实际只申请 `ohos.permission.INTERNET`(已核对提交包内 `module.json` ✓),照实写 |
   | 「截图含个人信息 / 尺寸不符」 | 用 `harmony/toolchain/capture_store_screenshots.py` 重拍(严格 16:9) |
   | 「分类 / 年龄分级不符」 | 改应用分类标签、重填年龄分级问卷 |
   | 「应用名称与已有应用重复 / 不规范」 | 改应用名(包名 `com.sabernotes.saber` 与上游 Android 版 `com.adilhanney.saber` 不冲突 ✓),同时改 `harmony/docs/store-listing.md` 与商店介绍里的名字 |
   | 「功能与描述不符 / 崩溃」 | 重新构建 `.app` 并**重新上传新版本**(versionCode 递增)再提交 |
   | 「图标有透明背景 / 与终端图标不一致」 | 包内图标必须是 **512×512 RGB**(restool 对 ≤512 原样拷贝;给 1024 会被转码出 alpha=254),且内容要是商店那张 1024 的**精确缩放**;商店图标用 `harmony/toolchain/make_app_icon.py` 重新生成 |
   | 「缺资质证明 / 《官方授权书》」 | 把 `harmony/toolchain/make_audit_zip.py` 生成的 zip 传到**两个槽**:版本表单顶部的「审核附件」**和**「版权信息 → 授权书及其他材料」(后者只收 JPG/JPEG/BMP/PDF,所以 zip 里必须有 PDF) |
   | 「名称/图标与已有应用相似」 | 改名 + 换图标,并**把应用介绍、隐私政策网页、包内 app_name 一起同步**(报告原文的提醒) |

3. 需要改包时:改代码 → `flutter build app --release --build-name=<x> --build-number=<N+1>
   --dart-define=FLUTTER_OHOS_AOT_BUILD=true` → AGC 软件包管理上传新 `.app` → 版本页「去选择」选新包 → 提交审核。

   **发布签名包的完整步骤**(商店包必须用 release Profile 签):

   ```bash
   cd /root/hzq/saber-ohos/saber
   cp -f ohos/signing/app-release.p7b ohos/signing/app.p7b      # 换成发布 Profile
   APP_VERSION_NAME=1.0.3 APP_VERSION_CODE=1000003 bash harmony/scripts/build_ohos.sh --app
   cp -f /root/hzq/saber-ohos/.signing-backup/app.p7b.debug-20261118 ohos/signing/app.p7b  # 换回调试 Profile
   python3 harmony/toolchain/verify_app_package.py              # 8 项验收
   ```

   ⚠️ 版本表单里**离开页面会把「发布版本」重置**,所以顺序要固定:
   先传包 → 再填表单其它项 → 最后「去选择」选包 → 立即提交。
   ⚠️ 审核期间不要点「撤销审核」,也不要点「保存草稿」(会清掉已选的包)。
4. 每一轮结论都追加到本表,并在 [`DEPLOY-RECORD.md`](DEPLOY-RECORD.md) 里补一节细节。

### 「包内单层图要 1024×1024」这条:查清楚了,决定不硬改

报告原文(第 2 轮,应用功能 1,报告里明确写了**不阻塞**):

> 应用图标单层图尺寸为144px*144px,标准要求尺寸1024px*1024px,且需下载
> HUAWEI DevEco Studio 5.0.5.315或以上版本进行图标再处理。

**官方口径**([《生成单层图标》](https://developer.huawei.com/consumer/cn/doc/harmonyos-guides/ide-apply-generated-icon)):
单层图标是 DevEco Studio 的 **Image Asset** 功能生成的 —— 按 sdpi~xxxldpi 各个
限定词生成不同尺寸,前景/后景图层推荐 1024×1024。本机只有 command-line-tools,
没有 DevEco Studio,这个功能用不了。

**实测**(用 SDK 自带 restool 直接跑,不改工程文件):

| 配置 | 源图 | 包内产物 |
|---|---|---|
| `iconCheck: true`(hvigor 默认) | 1024×1024 RGB | **512×512** RGB |
| `iconCheck: false` | 1024×1024 RGB | **512×512** RGB |

→ 关掉 `iconCheck` 也一样被压到 512,说明 **512 是 restool 资源编译的硬上限**,
不是校验开关能绕过去的(这一点纠正了之前「iconCheck 是开关」的猜测)。

**结论**:想让包里出现 1024,只能手改**已签名**的 hap 再重新签名 —— 为一条
**报告里明说不阻塞**的可提升项去手工改签名产物,风险(把建议项变成新的打包错误)
大于收益,**不做**。当前状态已是工具链能给的最好结果:
包内 512×512 RGB 无 alpha、商店 1024×1024 RGB 无 alpha,两者是同一张母图的
精确缩放(比对差异 = 0)。

硬件级加密 ✓),但**鸿蒙端没有这个插件** —— 我们用
`harmony/packages/stow_secure` 替代,底层是 `shared_preferences`,
落在应用沙箱内的 preferences 文件里,**就是明文**。那个包自己的注释里其实写得很清楚:

> 「它不像 KeyStore 那样提供硬件级加密,因此**不要**用它保存真正的密钥……
> 正式上架前建议替换为鸿蒙的 `huks`(密钥托管服务)实现。」

也就是说:我们发布出去的隐私政策,在「凭据怎么存」这件事上**写了句不成立的话** ——
审核员只要对照设置页/包体就能看出来,属于典型的「隐私声明与实际不符」✗✗。

**处理**(如实写,不粉饰):

* 政策第 4 节改成「保存在本应用的私有目录(HarmonyOS 应用沙箱)里,不会上传、也不会同步到
  任何服务器;沙箱隔离保证其它应用读不到它们」✓;
* 紧接着加一条「技术说明(如实告知)」:本 HarmonyOS 版本**尚未**接入 HUKS,
  凭据与**本机的笔记加密密钥**在本机**不是**硬件加密存放的,后续版本会改用 HUKS ✓;
* 英文摘要同步更正 ✓;
* 已推 gh-pages 并确认线上生效 ✓(`last-modified` 已更新)。

顺手核过另外两条加密相关的承诺,**都成立** ✓:

| 政策里的说法 | 代码里的依据 | 结论 |
|---|---|---|
| 「笔记在上传前会用**随机密钥**加密」 | `Key.fromSecureRandom(32)` + `IV.fromSecureRandom(16)`(`nextcloud_client_extension.dart`) | ✓ 真的随机 |
| 「笔记密钥在服务器上的副本由加密口令保护」 | `Encrypter(AES(passwordKey))`,口令 + salt 派生 | ✓ 属实 |

界面文案里没有任何「凭据已加密保存」的说法 ✓(只有 i18n 里一句「笔记会保持加密」✓ 属实),
商店文案也没写 ✓ —— 需要改的只有政策网页这一处 ✓。
